## 6. 캘린더 금액 9자리 이상 넘침

**현상/생긴 경위**

8자리 정도까지만 들어가고 9자리부터 잘린다. 코드 위치: `Calendar.tsx` ledger
변형 금액 영역.

참고: 대시보드 미니 캘린더(mini 변형)는 QA-047에서 수입/지출 표기를 8자리
표시 후 `...` 로 자르는 방식(`truncateDigits`, `src/utils/currency.ts`)으로
먼저 적용했다. 이 화면(ledger 변형)은 아직 그 방식을 적용하지 않았다 —
같은 방식을 쓸지도 함께 물어볼 것.

**물어볼 것**

표기 방식(만·억 축약 / 자동 축소 / 상한 표기 후 `...`) 디자이너 확인 필요.

**답 (디자이너, 2026-10-27)**

자릿수를 넘어가면 만·억처럼 한글 단위로 축약해서 표기하는 방식으로 간다. 해당 케이스
화면은 디자이너가 추가로 만들어 줄 예정.

**할 일**

추가될 케이스 화면을 받아서 `Calendar.tsx` 의 ledger 변형 금액 렌더링에 한글 단위 축약을
적용한다. 몇 자리부터 줄이는지 · 소수점 여부 · 단위 표기 형식은 그 화면으로 확인한다(답에는
없었다). 미니 캘린더(mini 변형)가 지금 쓰는 8자리 후 `...`(`truncateDigits`)을 같은
축약으로 바꿀지도 그 화면에서 같이 확인한다. 적용하고 나면 이 항목을 지운다.

## 9. TextField 밑줄(언더라인) 완전 제거 여부

**현상/생긴 경위**

2차 디자인 QA에서 서로 다른 두 화면(회원가입/로그인 코멘트 #6 — 로그인 입력칸,
내역 코멘트 #14 — 내역 금액 입력칸)이 똑같이 "입력 중에도 밑줄이 보인다,
밑줄 없이 텍스트만 입력돼야 한다"고 지적했다. 코드 위치는 공용
`TextField.tsx`(`src/components/Input/Text Field/TextField.tsx:139,252`)인데,
이 밑줄은 지금 포커스(파란색)·오류(빨간색)·성공 상태를 구분해 보여주는 용도로도
쓰인다(`underlineColor` 로직, `:121-127`).

**물어볼 것**

밑줄을 아예 없애면(완전 flat 디자인) 포커스·오류·성공 피드백을 다른 방식(예:
라벨 색상 변화, 헬퍼 텍스트만)으로 대체해야 하는지, 아니면 평상시(비어있고
포커스 없을 때)만 숨기고 포커스·오류 시에는 지금처럼 보여줘야 하는지. `TextField`는
앱 전역에서 쓰는 공용 컴포넌트라 기본값을 바꾸면 모든 입력 화면에 영향을 준다.

**답이 오면 할 일**

답에 따라 `TextField.tsx`의 `underlineColor`/`inputRow.borderBottomWidth` 로직 수정.

## 10. TextField label 타이포 — 화면마다 다른 기대값 충돌

**현상/생긴 경위**

공용 `TextField`의 label은 지금 `Subtitle/Subtitle2`(16px/500, 색상 미지정)를
쓴다(`TextField.tsx:236-238`). 그런데 2차 QA에서 더보기 코멘트 #157(모임 프로필
수정 화면)은 이 label을 `Subtitle/Subtitle4`(14px/500) + `foreground/primary`로
바꿔야 한다고 했고, 회원가입 코멘트 #21(회원가입 정보입력 화면)은 같은 label이
지금 16px(Subtitle2)인 게 기대값과 맞다고 판정됐다. 같은 컴포넌트의 같은
속성에 대해 서로 다른 화면이 서로 다른 크기를 요구하는 셈이라, 하나로
통일하면 다른 쪽이 깨진다.

**물어볼 것**

label 타이포가 화면(회원가입 입력 / 모임 프로필 수정 등)에 따라 실제로 달라야
하는지, 아니면 둘 중 하나가 Figma 상 오래된 코멘트인지.

**답이 오면 할 일**

같아야 한다면 `TextField.tsx`의 `label` 스타일 하나만 수정. 화면별로 달라야
한다면 `labelSize`/`labelColor` 같은 prop을 추가해 호출부마다 지정하도록 변경.

## 11. TextButton "tertiary" 색상 — Dialog 취소 버튼 vs 로그아웃/탈퇴 버튼 충돌

**현상/생긴 경위**

공용 `TextButton`의 `tertiary` 계층은 지금 `foreground/neutral-normal`(#4B5563)
색을 쓴다(`src/components/Input/Button/TextButton.tsx:102-104`). 2차 QA에서
내역 코멘트 #72·#135(내역 상세 삭제 확인 Dialog의 "취소" 버튼)는 이 색이
`foreground/neutral-subtle`(#9CA3AF, 더 옅게)여야 한다고 했고, 더보기 코멘트
#30(내 프로필 화면의 로그아웃/탈퇴 버튼, 역시 `tertiary`)은 `foreground/primary`
(#070A23, 더 진하게)여야 한다고 했다. 같은 `tertiary` 색 하나를 양쪽 다 만족시킬
수 없다.

**물어볼 것**

"tertiary"가 맥락(다이얼로그 취소 vs 목록형 위험 버튼)에 따라 색이 달라야
하는 건지, 아니면 두 용도를 구분하는 새 계층(hierarchy)이 필요한지.

**답이 오면 할 일**

구분이 필요하면 `TextButton`에 계층을 하나 추가(예: `muted`)하고 `Dialog.tsx`의
취소 버튼과 `MyProfileScreen.tsx`의 로그아웃/탈퇴 버튼이 각자 맞는 계층을 쓰도록
호출부를 수정.

## 13. Dialog 확인 버튼 텍스트 — Body2/primary 기대값과 공용 TextButton 충돌

**현상/생긴 경위**

2차 QA 더보기 코멘트 #34(노드 76:18843, "확인 Text")는 Dialog의 확인 버튼
텍스트가 `Body2`(14px/400) + `foreground/primary`여야 한다고 했다. 그런데 확인
버튼은 공용 `TextButton.tsx`를 쓰고, 기본 라벨 타이포는 `Other/Button`(14px/600)
고정이며 색상은 `hierarchy` prop(Dialog는 `secondary`→파란색 또는 `negative`→빨간색)에
따라 정해진다(`TextButton.tsx:90-110`). Dialog 확인 버튼만 글자 굵기를 regular로
낮추고 색을 무조건 primary(네이비)로 바꾸면, `TextButton`을 쓰는 다른 화면(더보기
메뉴 리스트, 로그인 화면 등)에도 영향을 줄지, 아니면 Dialog 전용 예외가 필요한지
불명확해서 코드를 건들지 않았다. (바로 옆 노드인 #33 "확인 Text"는 Dialog 타이틀로
판단해 `H3`+`primary`로 이미 반영함 — 혼동 주의.)

**물어볼 것**

Dialog 확인 버튼만 `Body2`+`primary`로 바꿔야 하는지, 아니면 `TextButton`
전체의 기본 타이포/색상 체계를 바꿔야 하는지. 바꾼다면 기존 `secondary`(파란)/`negative`(빨간)
색상 구분은 그대로 유지하는지.

**답이 오면 할 일**

Dialog 전용이면 `Dialog.tsx`의 확인 `TextButton`에 별도 `labelStyle`/`hierarchy`
오버라이드 추가. 전역 변경이면 `TextButton.tsx`의 `label`/`*Label` 스타일 수정
(이 경우 design.md #11 — TextButton tertiary 색상 충돌 — 과 함께 재검토 필요).

## 14. ReportMainScreen 보고서 카드 — "전체" 탭 + 카드 구조 확장 요구

**현상/생긴 경위**

더보기 코멘트 #93(노드 76:20415)은 보고서 생성 메인 화면(`ReportMainScreen.tsx`)의
Report Card가 "전체탭 없음·단순 카드 구조"라고 지적했다. 지금 `Tabs`는 `장부별`/`기간별`
2개만 있고(`REPORT_TAB_BY_LEDGER`/`REPORT_TAB_BY_PERIOD`), 리스트 카드는 제목+생성일시만
보여준다(`styles.card`). 코멘트는 "전체"를 포함한 3탭 구조와 더 풍부한 카드 레이아웃(아이콘·
배지 등)을 기대하는 것으로 보이는데, 구체적으로 "전체" 탭이 두 타입을 합쳐 보여주는 것인지,
카드에 정확히 어떤 요소가 추가되어야 하는지는 캡처 캡션만으로 판단이 안 된다. 타입 필터
전체 보기를 추가하려면 `ReportType` 유니온이나 API 쿼리 스펙도 바뀔 수 있어 백엔드 영향도
있을 수 있다. (같은 노드 그룹의 #92 "생성 일시 Text"는 라벨 누락 건이라 이미
`REPORT_DETAIL_CREATED_AT_LABEL` 접두어 추가로 반영함.)

**물어볼 것**

"전체" 탭이 실제로 필요한지(필요하다면 API 쿼리 스펙 변경 필요), 카드에 추가되어야 할
요소가 구체적으로 무엇인지 — 목업 화면 필요.

**답이 오면 할 일**

API가 전체 조회를 지원하면 `ReportType`에 `'ALL'` 같은 값 추가하고 `TABS` 배열·
`reportService.getReports` 호출부 수정. 카드 레이아웃은 목업대로 `styles.card`/
`renderItem` 수정.

## 15. AllGroupsScreen 그룹 카드 — 이메일 필드 자체가 없음

**현상/생긴 경위**

더보기 코멘트 #110(노드 76:21102)은 전체 모임 관리 화면(`AllGroupsScreen.tsx`)의
그룹 카드(`EntityCard.tsx`의 `type: 'group'` variant)에 이메일 텍스트가 있어야
한다고 했다. 그런데 `Group` 타입(`src/types/group.ts`)에는 애초에 email 같은
필드가 없고, 모임(그룹) 자체가 이메일을 가질 이유가 설계상 불명확하다(개인 프로필
`type: 'profile'` variant는 이미 `email` prop을 받아 렌더링하고 있어 혼동 가능성
있음 — `EntityCard.tsx:89-91`). `EntityCard.tsx`는 2차 QA 1라운드에서 고친
14개 공용 컴포넌트에 포함되지 않은 컴포넌트라 임의로 건들지 않고 보류했다.

**물어볼 것**

그룹 카드에 실제로 이메일(또는 이메일처럼 보이는 다른 정보 — 가입 코드, 생성일 등)을
추가해야 하는지, 추가한다면 백엔드 `Group` 응답에 해당 필드가 있는지.

**답이 오면 할 일**

백엔드가 필드를 제공하면 `types/group.ts`의 `Group` 타입에 필드 추가하고
`EntityCard.tsx`의 `type: 'group'` variant에 `email`(또는 해당 필드) prop과
렌더링 로직 추가(`type: 'profile'`의 이메일 렌더링 패턴 재사용).
