# 기획 확인 대기

정책·동작·권한·흐름 결정이 필요해서 기획에게 물어야 하는 것들.

---

## 1. 내역 수정·삭제·승인 권한 — 일반 권한 관리자 배제

**현상/생긴 경위**

시안/요구는 "삭제 아이콘 항상 노출", "승인 요청은 관리자가 들어가서 바로 수정"
인데, Entry API 는 수정·삭제·승인 모두 OWNER(총무)만 허용한다(일반 권한
관리자가 자기 승인 대기 내역도 수정 못 함, 2026-08-17 확정). QA-038 에서는
API 기준대로 OWNER 에게만 앱바 아이콘(수정/삭제)과 승인하기 버튼을 노출했다.

**물어볼 것**

기획 의도가 "모든 관리자(MEMBER 포함)" 였다면 백엔드와 함께 권한을 넓혀야
한다. 지금 구현은 임의로 열지 않았다.

**답이 오면 할 일**

권한을 넓히기로 하면 `src/screens/Folder/TransactionDetailScreen.tsx` 의
OWNER 체크 조건을 넓혀야 한다. Entry API 쪽 권한 정책도 같이 바뀌어야 해서
`docs/pending/backend.md` 쪽 작업으로도 이어진다.

---

## 2. MEMBER가 승인 대기 내역을 눌렀을 때의 화면/동작

**현상/생긴 경위**

QA-038 로 MEMBER(일반 권한 관리자)는 내역 상세에서 앱바 아이콘·승인하기
버튼이 전부 사라진다. 조회만 가능한 화면이 맞는지, 아니면 "검토 요청" 같은
별도 동작이 있어야 하는지가 시안에 없다.

**물어볼 것**

MEMBER가 승인 대기 내역을 봤을 때 기대 동작.

**답이 오면 할 일**

정해진 동작에 맞춰 `src/screens/Folder/TransactionDetailScreen.tsx` 에 MEMBER
전용 분기(별도 버튼/안내 등)를 추가한다.

## 3. 캘린더 경로(hideActions)에서 숨길 범위

**현상/생긴 경위**

QA-038 은 "대시보드 미니캘린더 → CalendarScreen → 상세" 경로에서 앱바
아이콘만 숨겼다(hideActions). 행 수정 화살표, 사진 추가/삭제, 승인하기 버튼은
그대로 노출된다.

**물어볼 것**

이 경로로 들어왔을 때 행 수정 화살표·사진 추가/삭제·승인하기 버튼도 같이
숨겨야 하는지.

**답이 오면 할 일**

숨기기로 하면 `src/screens/Folder/TransactionDetailScreen.tsx` 의
`hideActions` 조건을 행별 수정·증빙 추가/삭제·승인하기 버튼에도 적용한다.

## 4. 스낵바 자동 닫힘 vs X 버튼

**현상/생긴 경위**

지금 스낵바는 1.6초 뒤 자동으로 사라지고 X 버튼이 없다. 시안상 스낵바에는
X 가 그려져 있다.

**물어볼 것**

자동으로 사라지게 둘지, X 로만 닫게 할지, 둘 다인지.

**답이 오면 할 일**

정책에 맞춰 `src/components/Feedback/Snackbar/Snackbar.tsx` 의 자동 숨김
타이머·X 버튼 노출 여부를 조정한다.

## 5. 약관 목록 범위 불일치 — 가입 3종 vs 설정 3종

**현상/생긴 경위**

백엔드 문서(2026-11-09)에서 지적: 가입 화면 약관 동의는 서비스·개인정보·마케팅
3종인데, 설정 > 약관 및 정책 목록(`TermsScreen.tsx`)은 서비스·개인정보·자동기록
3종이다. 서버가 가진 `termType` 은 SERVICE/PRIVACY/MARKETING/AUTO_RECORD 4종.

**물어볼 것**

설정 > 약관 및 정책 목록에 마케팅 동의 항목도 넣을지(4종으로), 아니면 지금처럼
자동기록까지만 3종으로 둘지.

**답이 오면 할 일**

4종으로 넓히기로 하면 `TermsScreen.tsx` 에 마케팅 카드 추가, `TermType` (현재
`supportService.ts` 에 `SERVICE | PRIVACY | AUTO_RECORD` 로만 선언됨)에
`MARKETING` 추가.

## 6. 문의하기 입력 제한 확인

**현상/생긴 경위**

백엔드가 화면명세에서 값을 못 찾아 제목 50자·내용 1000자·하루 5건으로 임의
결정해 배포했다(`POST /api/v1/inquiries`, 초과 시 429 `INQUIRY_LIMIT_EXCEEDED`).

**물어볼 것**

제목 50자·내용 1000자·하루 5건이 맞는지. 화면 글자 수 표시와 다르면 바꿀 값을
백엔드에 전달.

**답이 오면 할 일**

값이 다르면 `InquiryScreen.tsx` 의 글자 수 표시·`maxLength` 를 서버 값과
맞춘다. 429 안내 문구도 실제 제한 수치로 맞춰 쓴다.

## 7. 알림 문구·발생 조건 확인

**현상/생긴 경위**

백엔드가 알림 title/body 문구와 발생 조건(승인 요청·승인, 회비 생성·마감, 새
관리자 참여, 총무 권한 이전, 관리자 제외)을 자체적으로 정해 배포했다. 시안
문구와 다를 수 있다. 지금은 반려·회비 납부 상태 변경·공지 등록·마케팅 알림은
생기지 않는다.

**물어볼 것**

표의 title/body 문구가 시안과 같은지. 반려·납부 상태 변경·공지 등록 알림이
필요한지.

**답이 오면 할 일**

문구·발생 조건은 서버 쪽에서만 바뀐다(앱 코드 수정 없음, 받은 문구를 그대로
그림). 새 카테고리/대상이 필요해지면 백엔드에 다시 요청.
