# 디자인 ↔ 구현 상세 대조 (design-diff)

`docs/design-verification.md` §2 표의 비고 칸이 76개 화면 분량 상세 차이를 감당 못 해서 분리한 문서.
Screen ID별 섹션에 실제 대조 결과를 적는다. 비교 이미지는 `shots/pairs/<SCREEN_ID>.png`
(`npm run pair -- <SCREEN_ID>`로 생성, DESIGN 360폭 원본 | ACTUAL 1080→360 다운스케일 나란히 배치).

작성 기준: "비슷하다" 같은 감상 금지. 차이 없으면 "차이 없음"이라고 명시. 차이 있으면 고칠 파일:줄 표기.

캡처 조건: 에뮬레이터 1080x2340 @ 480dpi (xxhdpi, 3x) — 디자인 360dp 폭과 정확히 일치.
캡처 시각: 2026-08-28, `com.billage` 앱 데이터 초기화 후 목 계정 로그인 상태.

## 검증 방식 (파일럿 5개로 확정)

`shots/pairs/*.png` 360px 다운스케일 비교로 실제 판별 가능한 항목과 불가능한 항목이 갈린다.
아래 표대로 항목별 검증 수단을 나눈다 — 안 되는 걸 이미지로 계속 시도하는 건 시간 낭비다.

| 대조 항목 | 검증 수단 | 비고 |
|---|---|---|
| 레이아웃/여백·간격 | 이미지 대조 | 360px에서 구조적 차이(간격, 정렬)는 뚜렷이 보임 |
| 아이콘·이미지 에셋 | 이미지 대조 | 아이콘 유무/종류 차이는 뚜렷이 보임 (COM-1 소셜 아이콘 사례) |
| 색상(토큰 vs 하드코딩) | 이미지 대조 | 색 자체 차이는 보이나, "토큰을 썼는지 하드코딩인지"는 코드 확인 필요 |
| 텍스트 문구 | 이미지 대조 | 문구 자체는 육안 대조 가능 |
| 화면 상태(빈 목록/로딩/에러/긴 텍스트) | 이미지 대조 | 상태별로 캡처만 맞으면 판별 가능 (단, 디자인·실제 캡처가 같은 상태여야 함 — FDR-1 사례 참고) |
| 타이포(자간·행간 미세 차이) | **코드 대조로 이관** | letterSpacing 0~1.5dp 수준은 360px 이미지에서 육안 구별 불가 확인됨 (COM-1 파일럿). §B(`docs/typography-audit.md`)에서 전수 조사 |
| 인터랙션·상태(기본/눌림/비활성/포커스) | **별도 라운드로 분리** | 정적 스크린샷 1장으론 확인 불가. 이번 배치(§C 이하)부터 이미지 대조에서 제외 |

이후 이미지 대조 섹션에서는 위 5개 항목(레이아웃/여백, 아이콘·에셋, 색상, 텍스트 문구, 화면 상태)만
다룬다. 자간·인터랙션은 더 이상 이미지 대조 항목으로 쓰지 않는다.

## COM-1-PAGE-01-0 (로그인)

비교 이미지: `shots/pairs/COM-1-PAGE-01-0.png`

- **레이아웃/여백·간격**: 차이 있음. 디자인은 로고~이메일 필드 사이 간격이 더 크고, 이메일/비밀번호
  필드와 로그인 버튼 사이 간격도 더 넓다. 실제 구현은 전체적으로 위쪽에 요소가 몰려 있고 화면
  하단(소셜 로그인 아래)에 빈 공간이 많이 남는다. `src/screens/LoginScreen.tsx`의 세로 간격(marginTop/
  marginBottom, gap) 값 재조정 필요.
- **타이포(크기·굵기·행간·자간)**: 이 스케일(360px 폭)에서는 판별 불가. letterSpacing 값(0~1.5dp)이
  다운스케일 이미지에서 육안 구별 안 됨 — `src/constants/typography.ts`와 실제 적용 여부는 코드
  대조로 별도 확인 필요(이번 파일럿 범위 밖).
- **색상(토큰 vs 하드코딩)**: 차이 없음(육안상). 배경/텍스트 톤 동일해 보임.
- **아이콘·이미지 에셋**: 차이 있음.
  1) 앱 로고 — 디자인은 책 모양 아이콘 + "Billage" 워드마크 조합, 실제 구현은 워드마크만 있고
     아이콘 마크가 없다.
  2) 소셜 로그인 버튼 — 디자인은 카카오 말풍선 아이콘(노랑)·네이버 초록 아이콘·구글 멀티컬러 G
     로고를 사용. 실제 구현은 원형 배경 위에 글자만 있는 자리표시자(노랑 원+"K", 초록 원+"N",
     흰 원+"G" 텍스트)로 대체돼 있다. `src/screens/LoginScreen.tsx`의 소셜 로그인 버튼 렌더링부
     확인(현재 아이콘 SVG/이미지 미적용, 텍스트 이니셜로 임시 처리된 것으로 보임).
- **텍스트 문구**: 차이 없음. "이메일", "비밀번호", "로그인하기", "비밀번호를 잊으셨나요?",
  "회원가입하기" 모두 일치.
- **인터랙션·상태(기본/눌림/비활성)**: 이번 캡처는 기본 상태만 확보. 눌림/비활성 상태는 이번
  파일럿에서 캡처하지 않음(범위 밖).
- **빈 목록/로딩/에러/긴 텍스트**: 해당 없음(입력 폼 화면, 목록 없음).
- **기타(디자인에 없는 요소)**: "목 계정으로 로그인 (개발용)" 버튼은 개발 편의용으로 디자인에는
  당연히 없음 — 실제 결함 아님, 프로덕션 빌드에서 제외되는지만 별도 확인 권장.

## DTB-1-PAGE-01-0 (내역 메인)

비교 이미지: `shots/pairs/DTB-1-PAGE-01-0.png`

- **레이아웃/여백·간격**: 차이 없음. 요약 카드, 탭, 필터/검색 아이콘, 리스트 항목 간격 모두 디자인과
  일치하는 구조.
- **타이포**: 이 스케일에서 판별 불가(위 COM-1-PAGE-01-0과 동일 사유).
- **색상**: 차이 없음. "승인요청" 배지 배경(연노랑), "전체 내역" 활성 탭 밑줄(파랑), 수입 금액(파랑)/
  지출 금액(검정) 색 구분 모두 일치.
- **아이콘·이미지 에셋**: 차이 있음. 리스트 항목 우측에 아이콘이 붙는 조건이 다르다. 디자인 캡처의
  "(주)이마트" 항목엔 사각 문서 아이콘이 있고, 실제 데이터의 "레크레이션 경품"/"주류 구매" 항목엔
  각각 "승인요청" 배지 또는 문서 아이콘이 붙어 있음 — 이건 데이터셋이 달라서 생기는 차이(시드 데이터
  불일치)로 보이며, 컴포넌트 자체의 결함은 아님. 실제 결함 여부 판단하려면 동일한 항목 데이터로
  재캡처 필요.
- **텍스트 문구**: 차이 없음. "수입"/"지출"/"합계"/"전체 내역"/"승인요청"/"N 건" 형식 모두 일치.
  금액·건수 숫자는 시드 데이터 차이(디자인 70,000원/24건 vs 실제 2,400,000원/24건)이지 문구 결함
  아님.
- **인터랙션·상태**: 기본 상태만 확보. 미캡처.
- **빈 목록/로딩/에러/긴 텍스트**: 해당 화면엔 항목이 있어 빈 상태 미확인. 별도 캡처 필요(범위 밖).

## FDR-1-PAGE-01-0 (폴더 메인, 그리드 뷰)

비교 이미지: `shots/pairs/FDR-1-PAGE-01-0.png`

- **레이아웃/여백·간격**: 차이 있음. 디자인은 상단에 검색창이 있고 바로 아래 "N 건" 카운트가 오지만,
  실제 캡처는 검색창에 이미 검색어("여름 MT")가 입력된 상태로 캡처됨 — 그 결과 디자인 이미지가
  "검색 중" 상태(빈 결과 화면+키보드)이고 실제 캡처가 "기본 목록" 상태라 **같은 상태끼리 비교가
  안 됐다**. 이건 워크플로 결함(디자인 이미지 매칭 실패)이지 앱 결함이 아님 — 아래 §5 평가에서
  다룸. 기본 그리드 목록 상태끼리는 재비교 필요.
- **타이포**: 판별 불가(스케일 사유, 위와 동일). 상태 불일치로도 비교 무의미.
- **색상**: 판별 가능한 범위(실제 캡처만) 내에서 폴더 아이콘 파랑, 파일 아이콘 회색 — 정상.
  디자인과 직접 대조는 상태 불일치로 보류.
- **아이콘·이미지 에셋**: 실제 캡처 기준 폴더/파일 아이콘 렌더링 정상. 디자인과 직접 대조 불가
  (상태 불일치).
- **텍스트 문구**: 실제 캡처의 "검색어를 입력해주세요." placeholder, "6 건" 카운트 문구 자체는
  이상 없음. 디자인 쪽 문구("해당 검색어에 대한 내역이 없어요." 등)는 다른 상태(빈 검색 결과)라서
  직접 대조 대상이 아님.
- **인터랙션·상태**: 오히려 이번 캡처 쌍이 "기본 목록 상태(실제) vs 검색 상태(디자인)"를 우연히
  나란히 보여준 셈 — 두 상태 다 앱에 존재하는 것은 확인됨(빈 상태 문구 존재는 디자인 이미지로
  간접 확인).
- **빈 목록/로딩/에러/긴 텍스트**: 디자인 이미지 자체가 빈 검색 결과 상태라 "해당 검색어에 대한
  내역이 없어요." 문구가 존재함은 확인. 이 문구가 실제 코드에도 있는지는 `src/screens/Folder/
  FolderScreen.tsx` 또는 `FolderSearchScreen`류에서 별도 확인 필요(이번 캡처로는 못 봄).
- **설계 이슈**: `design-index.json`에서 FDR-1-PAGE-01-0 기본값으로 고른 파일(`FDR/폴더/
  FDR-1-PAGE-01-0.png`, gridview/listview 서브폴더 밖의 파일)이 실제로는 "그리드 뷰의 검색 상태"
  이미지였다. 같은 Screen ID 아래 상태가 다른 이미지가 섞여 있어 "첫 번째(-0) 기본값" 규칙만으론
  부족함 — §5에서 상세 논의.

## ETC-1-PAGE-01-0 (더보기 메인)

비교 이미지: `shots/pairs/ETC-1-PAGE-01-0.png`

- **선행 확인**: `docs/shot-targets.tsv` 및 `docs/design-verification.md` §2에 이 화면 상태가
  "부족함"(빈 핸들러 메뉴)으로 기재돼 있었다. 별도 세션의 "더보기/모임 관리" 구현 작업으로
  `MoreScreen.tsx`가 부분 재구현됐지만, **전면 해소는 아니다** — 정정: "모임 관리" 항목(L102)만
  `navigation.navigate('GroupManager')`로 연결됐고, "보고서 생성"(L112)·"증빙자료 앨범"(L118)·
  "소비 통계/분석"(L124)·"보관함"(L130) 4개는 여전히 `onPress: () => {}` 빈 핸들러다(대상 화면
  자체가 아직 없음). **이전 버전의 이 섹션이 "빈 핸들러 문제가 해소됨"이라고 과장 서술한 것을
  A-3 stale 점검 중 자체 발견해 정정함.** 아래 대조는 실제 화면 기준.
- **레이아웃/여백·간격**: 차이 있음. 디자인은 "모임 관리자" 카드 아래 아바타가 4개+"+3" 형태로
  나열되고 "모임 관리" 항목과 카드 사이 간격이 실제보다 좁다. 실제 구현은 아바타 미리보기가
  "김 2"(이니셜 칩 1개+숫자) 형태로 단순화돼 있고, 카드와 하단 메뉴 사이 간격도 디자인보다 넓다.
  `src/screens/MoreScreen.tsx`의 모임 관리자 카드 아바타 미리보기 부분, 모임원 리스트를 몇 명까지
  아바타로 펼쳐 보여줄지 로직 확인 필요.
- **타이포**: 판별 불가(스케일 사유).
- **색상**: 차이 없음. 배지/아이콘/텍스트 색 모두 일치(회색조 아이콘, 파랑 "전체보기" 링크).
- **아이콘·이미지 에셋**: 차이 있음. 헤더 우측 아이콘이 디자인은 톱니바퀴(설정) 아이콘, 실제는
  종(알림) 아이콘이다. 이건 디자인 이미지가 다른 변형(설정 진입점 버전)일 가능성과, 실제 구현이

## 배치 E 공통 패턴

- **디자인 원본 파일 자체의 결함이 2건 나왔다** (ADD-2-SHEET-07-0의 더미 캘린더 데이터,
  ADD-4-SNACKBAR-01-0에서 최종 확인된 "4 선택" 오기). 둘 다 실제 구현이 오히려 더 정상이다 —
  이런 경우 실제 화면을 "고쳐야 할 결함"으로 잘못 분류하지 않도록 주의. 디자인 쪽 파일 재요청이
  필요한 항목으로 별도 관리하는 게 낫다.
- **상태 불일치로 대조 못한 게 이번에도 2건**(ADD-1-PAGE-01-0 탭 기본값, ADD-2-SHEET-04-0
  키보드 유무) — D-2로 사전 명세를 해뒀는데도 실제 캡처 시점에 "탭을 안 누른 채 열기"처럼 사소한
  실행 실수로 상태가 어긋난 경우다. 사전 명세는 판단 시간은 줄여줬지만 캡처 실행 자체의 정확도까지
  보장하진 못한다 — §5에서 다룸.
- **실사용 관점 결함 1건**(ADD-2-MODAL-01-0의 하드웨어 back 버튼 우회 — 이탈 방지가 시스템 back
  에서는 전혀 작동 안 함)은 디자인 대조로는 못 잡고 코드를 직접 봐야 나온 것. 이미지 대조만으로
  커버 안 되는 범주가 파일럿에서 예상한 대로(자간·인터랙션) 또 하나 늘었다 — "백그라운드 이탈
  경로" 같은 것도 이미지 대조 범위 밖이라는 뜻.

- **소셜/외부 브랜드 아이콘 자리표시자 문제**는 COM-1-PAGE-01-0에서만 나왔지만, 카카오/네이버/구글
  로그인은 앱 전역에서 이 로그인 화면 하나로 진입점이 몰려 있어 반복 화면이 아님 — 공통 컴포넌트
  이슈라기보다 단일 화면 이슈.
- **디자인 인덱스의 "상태 불일치" 문제(FDR-1-PAGE-01-0)**는 개별 화면 버그가 아니라 `design-index.json`
  생성/선택 로직의 구조적 한계 — 76개로 확장 시 반복될 가능성 높음(§5 참고).

# F-1. 한국어 줄바꿈 전역 조사

**가설**: RN Android `Text`의 `textBreakStrategy` 기본값이 한글 단어 중간을 끊는 원인이다.

**검증 1 — 기본값 확인(코드로)**: `node_modules/react-native/.../TextAttributeProps.kt`에서
`textBreakStrategy` 미지정 시 `DEFAULT_BREAK_STRATEGY = Layout.BREAK_STRATEGY_HIGH_QUALITY`로
떨어짐을 확인. 프로젝트 어디에도 `textBreakStrategy`를 지정한 곳이 없어(`grep` 결과 0건) 실제로
모든 `<Text>`가 이 기본값(HIGH_QUALITY)으로 렌더링됨 — 여기까지는 가설과 정합.

**검증 2 — 실기기 테스트(직접 고쳐서 확인)**: `QuickServiceCard.tsx`의 `label` `<Text>`에
`textBreakStrategy="simple"`을 임시로 추가하고 에뮬레이터에서 재확인. **"손쉽게 공유하는"이
여전히 "공유하"+"는"으로 끊겼다 — 가설 기각.** Android의 `BREAK_STRATEGY_SIMPLE`과
`BREAK_STRATEGY_HIGH_QUALITY`는 "어떤 지점에서 끊을 수 있는가"의 후보 자체는 같은 ICU 라인브레이크
규칙을 쓰고 "그 후보 중 무엇을 고르는가"(그리디 vs 전역 최적화)만 다르다 — 한글 음절 사이는 둘 다
합법적 줄바꿈 지점으로 취급하므로 strategy를 바꿔도 음절 중간 줄바꿈 자체는 막히지 않는다. 이건
사실 **한글 타이포그래피에서 정상 동작**이다(한글은 영어처럼 "단어" 단위 줄바꿈을 강제하지 않고,
음절 블록 단위로 줄바꿈하는 게 관례임 — 하이픈 없이 아무 음절에서나 끊는 중국어/일본어와 같은 부류).

**진짜 원인(재조사 결과)**: 텍스트 엔진 문제가 아니라 **레이아웃 폭 문제**다.
`QuickServiceCard.tsx`(간편 서비스 카드, 3열 그리드)의 label 텍스트 박스 실측 폭이 72dp
(`bounds="[108,1692][324,1788]"`, 216px÷3)인데, "손쉽게 공유하는"은 한글 8글자라 body3(12px)
기준으로 최소 96~110dp가 필요하다 — **애초에 한 줄에 안 들어가는 폭**이라 어떤
`textBreakStrategy`를 쓰든 줄바꿈은 일어난다. 디자인 쪽은 카드 폭 대비 텍스트가 상대적으로 더
여유 있게 잡혀 있어(또는 폰트 크기가 더 작아) 한 줄에 들어간 것으로 보인다.

**전역 적용 여부**: 하지 않음 — 가설이 기각됐으므로 전역 플래그로 고칠 수 있는 문제가 아니다.
DSH-1 재캡처로 "고쳐졌는지" 확인하는 절차 자체가 성립하지 않음(애초에 안 고쳐짐을 위 테스트에서
이미 확인). `textBreakStrategy="simple"` 실험 코드는 되돌렸다(원상 복구 확인함).

**영향 범위**: 이번 조사로 확정된 건 `QuickServiceCard.tsx` 1곳뿐이다. 사용자가 지목한 "ADD 배치에서
독립적으로 나온 사례"는 이번 재검토 결과 **찾지 못했다** — E-1에서 캡처한 14개 ADD 화면 재확인
결과 유사한 폭 부족형 줄바꿈은 없었다(짧은 필드 라벨/시트 타이틀/스낵바 1줄 문구뿐이라 애초에
줄바꿈이 일어날 만한 후보가 없었음). 이전 보고에서 "DSH-1과 ADD 배치" 표현은 부정확했다 — DSH-1
1건만 확인된 것으로 정정한다. "카드처럼 폭이 좁은 컨테이너에 긴 한글 문구가 들어가는 다른 화면이
더 있는지"는 76개 전체를 눈으로 훑어야 확정되는 문제라 이번 조사 범위 밖 — §F-3 기획 확인 목록에
"전수 확인 필요" 항목으로 남긴다.

**결론**: 화면별(정확히는 컴포넌트별) 개별 이슈로 유지. `QuickServiceCard.tsx`의 카드 폭/패딩/
폰트 크기 중 하나를 조정해야 하는데, 이건 디자인 의도(카드를 3열로 유지할지, 라벨을 2줄로
자연스럽게 감쌀지)에 대한 판단이 필요해 이번 조사에서는 고치지 않았다 — 코드 수정 허가는
"가설이 맞을 때"로 조건부였고 가설이 틀렸으므로 적용 안 함.

## 0. 데이터 준비 중 발견한 것 (본론 전에 반드시 알아야 할 것)

- **서버가 회비 생성(`POST /groups/{groupId}/dues`)에서 갑자기 500을 내기 시작했다.** 처음
  한 번(`MT_2026`, `startDate` 미래)은 앱 UI로 정상 생성됐는데, 그 직후부터 같은 그룹에 대해
  같은 요청(같은 페이로드, 같은 계정, 유효한 토큰 — `GET`은 계속 200)을 curl로 반복해도
  전부 `{"code":"INTERNAL_ERROR"}`(500)만 돌아왔다. 날짜를 과거/오늘/미래로 바꿔봐도 동일—
  최초 1건 이후 이 그룹에 대한 회비 생성 자체가 서버 쪽에서 막힌 것으로 보인다. **코드 문제
  아님, 이번 라운드에서 원인 특정 못함** — 다음에 회비 화면을 만질 때 서버팀 확인 필요.

### 의도적 차이 vs 빠뜨린 것 비율

"사소"(이미 고친 항목 재확인 3건)를 뺀 나머지 실질적 차이 7건 중:

  요청하기" 버튼, 체크박스+CTA. 셋 다 파일 상단 주석이 "7-B에서 붙인다" 또는 "알림 도메인
  부재로 뺐다"고 명시.
- **빠뜨린 것으로 보임(근거 문서·주석 없음)**: 3건 — 회비 상세 캐러셀 카드를 정적 단일
  카드로 단순화(정보 손실은 없으나 미문서화), 모임원 개별 추가 "이름 필수(`*`)" 표시 누락,
  태그 입력 진입점의 컴포넌트 형태(칩+필 버튼 vs `SelectionListItem` 로우) 차이.
- **버그(둘 다 아님)**: 1건 — 회비 상세 회원 목록이 화면에 안 보이는 렌더링 문제. 의도적으로
  뺀 것도, 몰라서 안 만든 것도 아니라 "만들 때는 됐는데 지금은 안 되는" 회귀성 버그로 본다.
- 비율: **의도적 3 : 빠뜨린 것 3**, 버그 1건은 별도.
