#### 배치 C 공통 패턴 — `marginTop:'auto'` 5곳 각각 재대조 [2026-08-28 배치 C]
- **"CTA 버튼 하단 고정" — D-3 조사 결론(공통 컴포넌트 아님, 반복되는 CSS 관용구임).**
  COM-1(로그인)과 COM-5(가입 완료) 코드를 직접 대조한 결과:
  - **공통 래퍼는 없다.** `LoginScreen.tsx`와 `SignupCompleteScreen.tsx`는 서로 다른 로컬
    `StyleSheet.create`만 쓰고, 공유하는 레이아웃 컴포넌트를 import하지 않는다.
  - **두 화면의 원인 자체가 다르다.** `SignupCompleteScreen.tsx:90`은 `footer: { marginTop: 'auto',
    paddingBottom: 24 }`로 버튼을 명시적으로 화면 최하단에 고정한다 — 디자인과 어긋나는 진짜
    원인. 반면 `LoginScreen.tsx`엔 `marginTop:'auto'`나 그 비슷한 하단 고정 코드가 전혀 없다 —
    `container`가 그냥 `flex:1, alignItems:'center', paddingTop:80`로 위에서부터 쌓이는 일반
    레이아웃이고, 디바이스 높이가 남아서 생기는 빈 공간일 뿐이다. **겉보기 증상(콘텐츠와 CTA
    사이 큰 여백)은 같지만 코드 원인은 서로 다르다** — 하나를 고친다고 둘 다 해결되지 않는다.
  - **그래도 진짜 반복은 있다.** `marginTop: 'auto'` 하단 고정 관용구 자체는 `grep`으로 전수
    검색한 결과 코드베이스에 **5곳**에서 쓰인다: `SignupCompleteScreen.tsx`(COM-5, 디자인 불일치
    확인됨), `EmailVerificationScreen.tsx`(COM-4, 상태 불일치로 이번엔 직접 대조 못 함),

    `LedgerCreateScreen.tsx`(FDR-3-PAGE-03-0, 디자인 이미지 자체가 없어 대조 불가). 공통
    컴포넌트로 묶여있진 않지만(각자 로컬 스타일에 복사된 관용구), **같은 코드 패턴이라 같은
    방식으로 어긋날 가능성이 높다** — 나머지 4곳을 캡처할 차례가 오면 이 항목부터 확인해라.

#### DUE-4-PAGE-01-0 (모임원 개별 추가) — 이름 필수(`*`) 표시·태그 진입점 형태 [2026-09-05 배치 G]
시안: `DUE-4-PAGE-01-0-1.png`(태그 있음), `-2.png`(빈 상태)

- **요소 누락**: **[누락]** "이름" 라벨에 필수 표시(`*`)가 없다. 시안엔 "이름" 옆에 파란 `*`가
  붙어 있는데(전화번호엔 없음 — 이름만 필수), 현재 구현(`TextField` 사용)엔 필수 여부를
  시각적으로 나타내는 방법 자체가 없다. 기능적으로는 이름 없으면 제출 버튼이 비활성화되니
  "필수"가 강제되긴 하지만, 시각적 표시가 빠졌다. **빠뜨린 것** — 의도적으로 뺐다는 근거(주석
  등) 없음.
- **형태 차이**: **[형태 차이, 빠뜨린 것에 가까움]** "태그" 입력 진입점의 컴포넌트 형태가
  시안과 다르다. 시안은 확정된 태그가 라벨 바로 아래 칩(`#개발 ✕`)으로 나열되고, 그 옆/아래에
  점선 테두리의 **"+ 추가하기" 필(pill) 버튼**이 있어 이게 태그 입력 화면으로의 진입점이다.
  현재 구현(`MemberAddIndividualScreen.tsx` L204-211)은 `SelectionListItem`(카드형이 아니라
  "타이틀 + 값 텍스트 + 화살표"인 목록 로우, `type="picker"`)을 재사용해서 태그가 없으면
  "선택사항", 있으면 `#태그1 #태그2`를 값 텍스트로 압축해 한 줄로 보여준다 — 확정된 태그가
  칩으로 개별 표시되지 않고, "+ 추가하기" 필 버튼도 없다. 정확히 이번 작업 지시에서 예로 든
  "카드형 선택 vs SelectionListItem 로우" 패턴 그 자체다. 이 화면 하나만 고치는 문제라 공용
  컴포넌트 파급은 없다(§ 공용 컴포넌트 영향 분석 참고).
- **텍스트 문구**: 차이 없음("이름을 입력해주세요.", "전화번호를 입력해주세요.", "메모를

#### `FolderItem` 리스트 아이콘 65dp — 시안 대조 대기 [2026-09-19 6-9]
`FolderGraphic`(65×51)/`LedgerGraphic`(60×50)은 `layout`을 안 받는 고정 크기 하나이고, list일 땐 그걸 `iconSlot`(폭 65, 가운데 정렬)에 넣을 뿐이다. 그리드/리스트 아이콘이 같은 크기인 건 코드대로다.

| 컴포넌트 | 아이콘 | 행 패딩/좌우 | 행 높이(코드로 계산) | 행 구분선 |
|---|---|---|---|---|
| `FolderItem list` | 폴더 65×51 / 장부 60×50 | 컨테이너 padding 12(상하좌우) + 화면 body 24 = **좌측 36** | 24 + max(아이콘 51, 텍스트 16+2+16=34) = **75dp** | 없음 |
| `SelectionListItem` | 셰브론 14×14(우측) | paddingVertical 14 | 28 + 20 = 48(부제 있으면 +18 = 66) | 없음 |
| `CheckListItem` | 체크 18×18(우측) | paddingV 12, paddingH 16 | 24 + 20 = 44 | 없음 |
| `MemberListItem` | 없음 | paddingV 12 | 24 + 20 = 44 | 없음 |
| `TransactionListItem` | 영수증 18×18(우측 열) | paddingV 12, paddingH 12(−12 마진 상쇄) | 24 + max(좌 16+4+20=40, 우 18+4+20=42) = 66(아이콘 없으면 64) | 없음 |

실측(132306 캡처, 표시 좌표×1.17÷3): 아이콘 폭 ≈65dp·높이 ≈51dp·좌측 ≈36dp·행 피치 ≈75dp로 코드값과 일치(±1dp). 리스트 행 아이콘의 앱 내 표준은 없다 — 다른 리스트형은 아이콘이 14~18dp 우측 보조 아이콘이고, 좌측 대형(65dp) 그래픽은 `FolderItem list`뿐이다. 65dp가 맞는지는 시안 대조 대기(수정 안 함).

#### F-1 한국어 줄바꿈 — QuickServiceCard 카드 폭/폰트 조정 방향 결정 [배치 F]
**가설**: RN Android `Text`의 `textBreakStrategy` 기본값이 한글 단어 중간을 끊는 원인이다.

**검증 1 — 기본값 확인(코드로)**: `node_modules/react-native/.../TextAttributeProps.kt`에서
`textBreakStrategy` 미지정 시 `DEFAULT_BREAK_STRATEGY = Layout.BREAK_STRATEGY_HIGH_QUALITY`로
떨어짐을 확인. 프로젝트 어디에도 `textBreakStrategy`를 지정한 곳이 없어(`grep` 결과 0건) 실제로
모든 `<Text>`가 이 기본값(HIGH_QUALITY)으로 렌더링됨 — 여기까지는 가설과 정합.

**검증 2 — 실기기 테스트(직접 고쳐서 확인)**: `QuickServiceCard.tsx`의 `label` `<Text>`에
`textBreakStrategy="simple"`을 임시로 추가하고 에뮬레이터에서 재확인. **"손쉽게 공유하는"이
여전히 "공유하"+"는"으로 끊겼다 — 가설 기각.** Android의 `BREAK_STRATEGY_SIMPLE`과
`BREAK_STRATEGY_HIGH_QUALITY`는 "어떤 지점에서 끊을 수 있는가"의 후보 자체는 같은 ICU 라인브레이크
규칙을 쓰고 "그 후보 중 무엇을 고르는가"(그리디 vs 전역 최적화)만 다르다 — 한글 음절 사이는 둘 다
합법적 줄바꿈 지점으로 취급하므로 strategy를 바꿔도 음절 중간 줄바꿈 자체는 막히지 않는다. 이건
사실 **한글 타이포그래피에서 정상 동작**이다(한글은 영어처럼 "단어" 단위 줄바꿈을 강제하지 않고,
음절 블록 단위로 줄바꿈하는 게 관례임 — 하이픈 없이 아무 음절에서나 끊는 중국어/일본어와 같은 부류).

**진짜 원인(재조사 결과)**: 텍스트 엔진 문제가 아니라 **레이아웃 폭 문제**다.
`QuickServiceCard.tsx`(간편 서비스 카드, 3열 그리드)의 label 텍스트 박스 실측 폭이 72dp
(`bounds="[108,1692][324,1788]"`, 216px÷3)인데, "손쉽게 공유하는"은 한글 8글자라 body3(12px)
기준으로 최소 96~110dp가 필요하다 — **애초에 한 줄에 안 들어가는 폭**이라 어떤
`textBreakStrategy`를 쓰든 줄바꿈은 일어난다. 디자인 쪽은 카드 폭 대비 텍스트가 상대적으로 더
여유 있게 잡혀 있어(또는 폰트 크기가 더 작아) 한 줄에 들어간 것으로 보인다.

**전역 적용 여부**: 하지 않음 — 가설이 기각됐으므로 전역 플래그로 고칠 수 있는 문제가 아니다.
DSH-1 재캡처로 "고쳐졌는지" 확인하는 절차 자체가 성립하지 않음(애초에 안 고쳐짐을 위 테스트에서
이미 확인). `textBreakStrategy="simple"` 실험 코드는 되돌렸다(원상 복구 확인함).

**영향 범위**: 이번 조사로 확정된 건 `QuickServiceCard.tsx` 1곳뿐이다. 사용자가 지목한 "ADD 배치에서
독립적으로 나온 사례"는 이번 재검토 결과 **찾지 못했다** — E-1에서 캡처한 14개 ADD 화면 재확인

#### 캐러셀 peek — peek 없는 페이지 스냅이 의도인지 시안 확인, 안 A/B 선택 [2026-09-19 6-9]
대상 캐러셀은 `LedgerDetailScreen`, `ReportPeriodEntriesScreen` 2곳(둘 다 2026-09-18 스냅 결함 수정본): `ScrollView horizontal pagingEnabled`, 슬라이드 폭 = `windowWidth`, 슬라이드 `paddingHorizontal: 24`(카드 폭 312), 스크롤뷰 자체 패딩/`snapToInterval`/gap 없음. 360dp 검산:

|---|---:|---|---|
| 페이지 0 | 0 | 24–336 | 384–696 (화면 밖, peek 없음) |
| 페이지 1 | 360 | −336–−24 (화면 밖, peek 없음) | 24–336 |

즉 **양쪽 모두 peek이 없고 대칭**이다. `132315` 캡처를 원본 픽셀로 샘플링해도 y≈380px 행에서 카드가 24dp에서 시작해 336dp에서 끝나고 336–360dp는 배경색이라 카드 2 sliver가 없다. 요청서의 "카드2가 348dp부터"(24+312+12)는 **2026-09-18 수정 전 코드**(스크롤뷰 paddingLeft 24 + 카드 312 + gap 12, `snapToInterval` 324)의 값과 일치하고 현재 캡처·코드와는 안 맞는다 — 그 수치가 어느 번들에서 나왔는지는 확인 불가(캡처 파일에서는 재현 안 됨). 현재 상태가 "peek 없는 페이지 스냅"이라는 설계 자체가 의도인지 시안 확인이 필요해 **수정하지 않고 판단 보류**. 만약 peek을 원한다면 안: **(A)** peek을 두는 구조(카드 폭 312 + gap 12 단위 `snapToInterval`, 스크롤뷰 양쪽 `contentInset`/패딩 24)로 재설계 — 단 2026-09-18 스냅 결함이 바로 이 구조(좌측 인셋을 스냅 간격에 반영 못 함)에서 났으므로 양 끝 페이지의 인셋 보정이 필요, **(B)** 지금처럼 페이지 스냅을 유지하고 peek 없음을 명세화. 어느 쪽인지는 시안(예: `더보기_보고서생성_기간보고서조회.png`, 장부 상세 명세)에 peek 표현이 있는지에 달려 있다.

## 4. 검증 방식 (파일럿 5개로 확정)

`shots/pairs/*.png` 360px 다운스케일 비교로 실제 판별 가능한 항목과 불가능한 항목이 갈린다.
아래 표대로 항목별 검증 수단을 나눈다 — 안 되는 걸 이미지로 계속 시도하는 건 시간 낭비다.

| 대조 항목 | 검증 수단 | 비고 |
|---|---|---|
| 레이아웃/여백·간격 | 이미지 대조 | 360px에서 구조적 차이(간격, 정렬)는 뚜렷이 보임 |
| 아이콘·이미지 에셋 | 이미지 대조 | 아이콘 유무/종류 차이는 뚜렷이 보임 (COM-1 소셜 아이콘 사례) |
| 색상(토큰 vs 하드코딩) | 이미지 대조 | 색 자체 차이는 보이나, "토큰을 썼는지 하드코딩인지"는 코드 확인 필요 |
| 텍스트 문구 | 이미지 대조 | 문구 자체는 육안 대조 가능 |
| 화면 상태(빈 목록/로딩/에러/긴 텍스트) | 이미지 대조 | 상태별로 캡처만 맞으면 판별 가능 (단, 디자인·실제 캡처가 같은 상태여야 함 — FDR-1 사례 참고) |
| 타이포(자간·행간 미세 차이) | **코드 대조로 이관** | letterSpacing 0~1.5dp 수준은 360px 이미지에서 육안 구별 불가 확인됨 (COM-1 파일럿). §B(`docs/typography-audit.md`)에서 전수 조사 |
| 인터랙션·상태(기본/눌림/비활성/포커스) | **별도 라운드로 분리** | 정적 스크린샷 1장으론 확인 불가. 이번 배치(§C 이하)부터 이미지 대조에서 제외 |

이후 이미지 대조 섹션에서는 위 5개 항목(레이아웃/여백, 아이콘·에셋, 색상, 텍스트 문구, 화면 상태)만
다룬다. 자간·인터랙션은 더 이상 이미지 대조 항목으로 쓰지 않는다.
