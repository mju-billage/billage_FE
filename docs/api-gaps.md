**확인 요청**: 사용자가 제시한 다섯 번째 후보 "회원 탈퇴"(`COM-1-PAGE-02-0` 등)는 전수 확인 결과 **이 카테고리에 해당하지 않는다** — `src/` 전체를 `grep`해도 탈퇴 관련 화면 코드나 로직이 전혀 없다(`design-verification.md`에도 `[미구현]`으로 표시돼 있어 화면 자체가 없는 상태). API도 없고(User 도메인엔 조회/수정만 있음) 화면도 없는, "둘 다 없는" 상태라 (A)가 아니라 (B)와 (A) 사이의 회색지대다 — 화면부터 만들어야 이 항목이 성립한다.

### 정책 결함 (필드 누락이 아니라 API 사용 방식 자체가 막힌 것)

| 항목 | 내용 |
|---|---|
| **초대코드 발급이 멱등하지 않음 — 조회 API도 없음** | `POST /groups/{groupId}/invitations`를 부를 때마다 서버가 **매번 다른 코드**를 새로 내려준다(실기기 확인: `SFA38DT7NH` → `DRXU9AMZTK`, 같은 모임인데도). "이미 발급된 유효 코드가 있으면 그걸 그대로 달라"는 조회 API가 없고, 발급 API 자체도 재호출 시 기존 코드를 재사용하지 않는다. 2단계에선 화면(`GroupManagerScreen`) 진입 시 캐시가 비어 있으면 자동 발급하는 방식으로 우회했는데, **디자인 시안(`ETC-2-PAGE-03-0.png`)을 다시 확인한 결과 화면엔 발급 버튼이 없고 코드가 상시 표시돼 있을 뿐**이라 "화면 진입 = 코드가 이미 있어야 한다"는 전제 자체는 시안과 맞다. 문제는 그 전제를 만족시키는 방법이 "진입할 때마다 재발급"뿐이라는 것 — 앱을 껐다 켤 때마다(캐시가 메모리에만 있어 재시작 시 비워짐) 서버에 새 코드가 쌓인다(이전 코드가 무효화되는지도 명세에 없어 불명). **2026-09-01 수정**: 화면 진입 시 자동 발급을 없애고, 기존에도 있던 "코드 카드를 탭하면(코드가 없을 때) 발급을 요청"하는 동작만 남겼다 — 새 버튼을 추가하지 않고 시안과 같은 정적 표시 상태를 유지하면서, 최소한 "화면을 열기만 해도 발급되는" 것은 막았다. 근본 해결은 아니다(재요청 자체는 여전히 새 코드를 만든다) — 백엔드에 필요한 것 중 **하나만** 있으면 된다: (1) 유효한 기존 초대코드를 조회하는 API, 또는 (2) 발급 API의 멱등성 보장(유효 기간 내 재호출 시 같은 코드 반환). |

### 필드/에러 코드 단위 공백 (2026-08-30, Group 1~2단계 연동 중 발견)

위 항목들과 달리 엔드포인트 자체는 있다 — 응답 필드나 에러 코드가 화면이 실제로 필요로 하는 것보다 좁다.

| 항목 | 어느 화면이 왜 필요로 하는가 |
|---|---|
| **`GroupMembership` 응답에 `email` 없음** | `ETC-3-SHEET-03-0/04-0`(모임원 프로필 시트)이 원래 이메일로 멤버를 식별하는 디자인인데(`GET /groups/{groupId}/memberships` 응답이 `membershipId·userId·name·role·joinedAt`뿐), 표시할 이메일이 없다. 2단계에서 이름+역할만으로 화면을 바꿔 우회했다 — 실제 이메일 표시가 꼭 필요하면 멤버마다 `GET /users/{userId}`를 추가 호출해야 하는데(N+1), 그럴 바엔 memberships 응답에 이메일을 포함해주는 쪽이 낫다. |
| **`GET /folders/{folderId}/ledgers` 응답에 `createdAt` 없음** | 3단계(Folder+Ledger) 작업 중 발견. 디자인 시안(`FDR-1-PAGE-01-0`, `FDR-2-PAGE-04-0`)은 폴더 목록의 장부 카드 서브타이틀에 생성일(`YY.MM.DD`)을 보여주는데, 장부 목록 응답엔 `ledgerId·folderId·name·budget·totalIncome·totalExpense·balance·remainingBudget·entryCount`뿐 `createdAt`이 없다(상세 조회 `GET /ledgers/{ledgerId}`에만 있음). 장부마다 상세를 추가 호출하면 N+1이 되므로, 목록 화면은 대신 예산 상태(`예산 N원`/`예산 미설정`)로 서브타이틀을 대체했다 — **실측 기반 가정 — 명세 확인 필요**: 목록 응답에 `createdAt`을 추가해주는 쪽이 정공법이다. |
| **`PATCH /ledgers/{ledgerId}`의 `folderId: null` 허용 여부 불명** | Folder.txt는 `PATCH /folders/{folderId}`의 `parentFolderId: null`(최상위로 이동)을 명시적으로 문서화하는데, Ledger.txt "4. 장부 수정"은 `folderId`를 보낼 수 있다고만 하고 `null`의 의미를 문서화하지 않는다. 3단계 다건 이동(`FolderMoveDestinationScreen`)에서 장부를 최상위로 옮기는 조합이 실제로 나올 수 있는 UI인데(목적지로 "전체"를 고를 수 있음), 이 조합만 UI에서 막아뒀다(`MOVE_DESTINATION_LEDGER_TO_ROOT_BLOCKED`) — **실측 기반 가정 — 명세 확인 필요**: 허용되는지, 허용된다면 그 장부가 이후 "최상위 영역 장부 조회" 공백(바로 아래 항목)에 그대로 걸린다는 것도 같이 확인해야 한다. |
| **Entry 등록/수정 API에 "담당자" 필드 없음** | 4단계(Entry) 작업 중 발견. `CLAUDE.md`("내역 추가(FAB): 금액/일자/장부/담당자/메모 입력")와 기존 화면(`TransactionRegisterScreen`의 담당자 선택 시트, `MANAGER_OPTIONS`)엔 이미 있는 필드인데, `POST/PATCH /ledgers/{ledgerId}/entries`, `PATCH /entries/{entryId}` 어디에도 담당자를 저장할 필드가 없다(`type/title/amount/occurredOn/memo/receiptFileIds`뿐). 화면 입력 필드 자체는 유지했지만(DTB 전체 목록 목 데이터 경로 `editMock`에서만 실제로 쓰인다) 실 Entry 등록/수정(`createReal`/`editReal`)에서는 이 값을 서버로 보내지 않는다 — 저장할 곳이 없어서다. 상세 조회 화면도 실 Entry일 땐 "담당자" 행 자체를 안 보여준다(서버가 안 주니까). |

### Entry+File 도메인 공백 (2026-09-01, 4-A 연동 중 발견)

| 항목 | 내용 |
|---|---|
| **`receiptFileIds`(내역 등록) 명세 자기모순** | Entry.txt 상단 배너는 "증빙 파일(`receiptFileIds`)도 File 도메인 구현로 활성화되었습니다"라고 하는데, 정작 "2. 내역 등록"의 Validation 절엔 "`receiptFileIds`: **미적용** — File 도메인 구현 전까지 요청에서 받지 않습니다"라는 상반된 문장이 그대로 남아 있다. File 도메인은 이미 "구현 완료"(File.txt)라 그 전제 조건은 충족됐다고 보고 상단 배너 쪽(활성화됨)을 따랐다 — **실측 기반 가정, 명세 정정 필요**: Validation 절 문구가 갱신 누락인지, 아니면 정말 등록(POST)에서만 아직 막혀 있는지 확인해야 한다. (수정 PATCH 쪽엔 이 "미적용" 문구가 없어 상대적으로 명확하다.) |
| **실제 카메라·갤러리 접근이 없어 File 업로드 API를 실제로 호출할 데이터가 없음** | `services/fileService.ts`(`uploadFile`)는 만들었지만 이번 라운드에 실제로 호출하는 화면이 없다. `MockCameraView`/`ReceiptScanningView`/`ReceiptGalleryPickerScreen`이 전부 실제 이미지 없이 `photo-${Date.now()}`/`scan-${Date.now()}`/`gallery-photo-N-${Date.now()}` 같은 가짜 문자열 토큰만 만든다(react-native-image-picker 등 실 라이브러리 자체가 프로젝트에 없음). 증빙 촬영/스캔/갤러리로 "첨부"해도 실 Entry 생성·수정 시 그 항목은 서버로 전송되지 않는다(가짜 토큰을 파일 id인 척 보내면 더 위험하다고 판단해 걸렀다) — 폼 안에서만 보이다가 제출 후엔 사라진다. **실 카메라/갤러리 라이브러리가 붙어야 진짜로 풀리는 항목**이라 API 연동만으로는 해결 불가. 기존에 서버에서 불러온 진짜 증빙(장부 상세→상세 조회, 수정 화면 프리필)은 정상 표시·삭제(전체 교체로 제외)된다 — 새로 추가하는 것만 막혀 있다. |
| **Entry 수정에 `ledgerId` 없음 — 등록 후 장부 이동 불가(사양, 버그 아님)** | `PATCH /entries/{entryId}` 요청 필드가 `title/amount/occurredOn/memo/receiptFileIds`뿐이라 내역을 다른 장부로 옮기는 기능 자체가 없다. `TransactionRegisterScreen`의 "장부" 선택 행은 실 내역 수정(`editReal`) 모드에서 탭 자체를 막아뒀다(표시만, 안내 문구 첨부). 신규 등록(`createReal`)에선 그대로 선택 가능. |
| **`LedgerCreateScreen` 진입 시 최상위 장부는 여전히 못 만듦 — 4단계에서 부작용 확인** | 3단계에서 이미 알려진 제약(최상위 장부 생성 API 없음)인데, 4단계에서 실사용 부작용을 하나 더 찾았다: `TransactionRegisterScreen`의 장부 선택 시트가 옵션이 0개일 때 보여주던 "새 장부 생성하기" 바로가기가 `LedgerCreateScreen`에 `parentId: null`을 그대로 넘기고 있었다(3단계 이전 코드) — 3단계에서 `LedgerCreateScreen`이 목 대신 실 API(`POST /folders/{folderId}/ledgers`, `folderId` 필수)로 바뀐 뒤로 이 진입 경로는 `parentId`가 없어 조용히 아무 일도 안 하는 죽은 링크가 됐다(폴더가 하나도 없는 새 모임에서만 실제로 마주친다). 이번에 그 바로가기 자체를 없앴다 — 고치려면 폴더부터 만들게 유도하는 경로가 새로 필요하다. |

## (C) 명세가 "추후 확정"으로 남긴 것 중 프론트가 막히거나 앞서간 지점

공통규칙 §16·§20·§21과 개별 도메인의 "확인 필요" 메모 기준.

| 항목 | 명세 상태 | 프론트가 앞서간/막히는 지점 |
|---|---|---|
| **파일 허용 확장자·용량·개수** (§16) | "추후 확정"(현재 구현값은 jpeg/png/webp, 10MB — 제안안) | 앱엔 이미 **"사진은 최대 10장까지 첨부할 수 있어요"** 제한 UI가 있다(`ADD-4-SNACKBAR-01-0`). 서버는 "한 요청의 최대 파일 개수"를 확정 안 했다 — 10장이 서버 정책과 맞는지 확인 필요. |
| **페이지네이션 적용 범위** (§20) | 미확정 | 현재 모든 목 리스트 함수(`getMyGroups`, `getAllTransactions` 등)가 페이지네이션 없이 전체 반환하는 형태로 짜여 있다. Entry/Dues/Report는 명세에 이미 `page/size` 응답 구조가 있으니 이 셋부터 연동 시 무한스크롤 UI를 새로 설계해야 한다. |
| **파일 업로드를 별도 API로 분리할지** (§20) | 미확정 | ADD 폼은 이미 "먼저 `POST /files`로 올리고 받은 `fileId`를 내역 등록에 같이 보내는" 분리형 흐름을 전제로 만들어져 있다(우연히 서버 제안과 일치하지만 공식 합의는 아직 없음 — 합의가 뒤집히면 폼 흐름을 다시 짜야 한다). |
| **생성·수정 권한 세부** (§21) | 일부만 확정(일반 관리자의 이름 수정·삭제 금지는 확정) | 현재 목 함수들은 `OWNER`/`MEMBER` 구분이 전혀 없어 **누구나 모든 CRUD가 가능**하다. 실제 연동 시 화면단에 권한 분기(버튼 비활성화 등)를 전부 새로 넣어야 하며, 서버가 `ACCESS_DENIED(403)`로 막는 지점과 프론트가 UI로 미리 막는 지점을 맞춰야 한다. |
| **폴더·장부 다건 이동 — 3단계에서 구현 완료, 서버 API는 여전히 단건뿐** | 명세는 `PATCH /folders/{folderId}` / `PATCH /ledgers/{ledgerId}` 단건만 제공 | `FDR-2-PAGE-01-0`(이동 대상 선택)의 체크박스 다중 선택을 그대로 살리기 위해 프론트가 선택 개수만큼 순차 `PATCH` 호출로 재구성했다(`FolderMoveDestinationScreen.tsx handleConfirm`, 병렬 아님 — 실패 순서를 명확히 추적하려고). 일부만 성공하면 롤백하지 않고(다건 트랜잭션 API가 없어 애초에 불가능) "N개 이동 완료, M개 실패했어요"로 그대로 알린다. 여전히 서버에 다건 이동 API가 생기면 이 순차 호출 코드는 걷어낼 수 있다. |
| **최상위 영역 장부 조회 — 폴더 해제(unlink) 구현 범위를 실제로 제한함(3단계에서 확인)** | Folder 명세 자체가 "확인 필요"로 남김(폴더 삭제 시 장부가 `folderId: null`이 되는데 조회 API가 없음) | `FDR-1-PAGE-01-0`(폴더 메인)은 이미 최상위에 폴더+장부가 섞여 보이는 UI다. 3단계에서 폴더 해제(`DELETE /folders/{folderId}`)를 실제로 붙이며 확인한 결과: **최상위가 아닌 폴더**를 해제하면 내부 항목이 조회 가능한 상위 폴더로 승격되므로 안전하지만, **최상위 폴더에 직속 장부가 있는 상태로 해제하면** 그 장부가 이 공백에 그대로 걸려 영구히 찾을 수 없게 된다. 그래서 이 조합(`parentId === null && ledgerCount > 0`)만 UI에서 막았다(`UNLINK_BLOCKED_DIALOG_*`, `FolderScreen.tsx`) — 나머지 해제는 전부 정상 작동한다. 이 API가 생기면 이 조건 분기 자체를 없앨 수 있다. |
